# Phase 4 — Performance Notes

The runtime chart and CSV in this folder were generated by the project's benchmark code. The measurements are averages of repeated runs using `time.perf_counter()`; Merge Sort and Dijkstra use five repeats, while the more expensive knapsack and route benchmarks use three. The generated benchmark data is deterministic (seed 42).

## Results snapshot

Times below are rounded from `runtime_results.csv` and are specific to the computer and Python environment used to generate them.

| Component | Input size | Average runtime |
|---|---:|---:|
| Merge Sort | 20 parcels | 0.110 ms |
| Merge Sort | 200 parcels | 0.472 ms |
| Knapsack, capacity 5,000 | 20 parcels | 13.872 ms |
| Knapsack, capacity 5,000 | 200 parcels | 205.706 ms |
| Dijkstra | 20 graph nodes | 0.042 ms |
| Dijkstra | 200 graph nodes | 0.245 ms |
| Nearest-neighbor route | 5 stops, 20-node graph | 0.385 ms |
| Nearest-neighbor route | 5 stops, 200-node graph | 3.540 ms |

## Interpretation

Knapsack takes longer here because its DP work grows with both parcel count and capacity (`O(nW)`). Merge Sort grows more slowly (`O(n log n)`). Dijkstra is very fast on these small sparse graphs, so it appears nearly flat when plotted beside knapsack on a linear shared y-axis. The nearest-neighbor benchmark holds the number of stops at five while increasing graph size; this isolates the effect of shortest-path work over a larger graph. The 20-versus-50 Merge Sort timings show normal noise for very short runs. These are sample measurements, not universal performance guarantees.

For a fair comparison, compare each algorithm's trend over its own input-size unit; parcel count, graph nodes, and delivery stops are different quantities.
